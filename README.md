## 2. Task & Calibration Summary
Task: `tasks/reconcile-bug` — fix `/app/reconcile.py`, a CSV payment-transaction reconciler (`tx_id,timestamp,amount,status` -> JSON `total_valid_amount / valid_count / failed_count`). The script is 76 lines.

- **Bug 1 (Easy):** the argument-count check is `len(sys.argv) < 1`, which can never be true, so running with no argument (or extra arguments) crashes with an `IndexError` traceback / silently accepts extras instead of printing `usage:` and exiting 2.
- **Bug 2 (Medium):** status filtering uses `else:` after the `FAILED` branch, so `PENDING` rows are counted as valid (inflating `valid_count` and `total_valid_amount`) instead of being ignored.
- **Bug 3 (Hard):** a bundle of six messy-input / duplicate-resolution rules. The business rules are stated in `instruction.md` (timestamps compared as absolute instants; a later `PENDING` row never replaces a final row; `tx_id` matching is case-insensitive; each amount rounded half-up to cents before summing), while the *data-format quirks* of real exports are only hinted at ("not always formatted uniformly"): Unix-epoch timestamps (the buggy parser silently skips them as "malformed"), a UTF-8 BOM that breaks the header so every row is skipped, and amounts like `"$1,234.50"`. An agent only finds those by testing on realistic data.
- **Calibration Scores:** `nop` = `0.00` | `oracle` (`solve.sh`) = `1.00` | Partial `oracle` (Bug 1+2 fixed, whole Bug 3 broken) = `0.40`; with only ONE Bug 3 sub-rule re-broken (the `rank` line, shown in video) = `0.90` | `hack.sh` = `0.00`

## 4. Trajectory Forensics (`trajectory.json`)
- **Where the Agent Failed in Run 1:** In trial `reconcile-bug__FCyd5kv` (0.80) the agent read `reconcile.py` (step 2), rewrote the whole file from the spec with a script `update.py` (step 5), and then only tested it with CSVs it invented itself (`test_all.py` in step 6, `test_edge.py` in step 8). It never looked at realistic export data: none of its 9 commands mentions epoch timestamps, a BOM, `utf-8-sig` or `fromtimestamp`. In step 9 it deleted its test files with `rm -f` and stopped. All 3 trials failed the `epoch` check and trials `FCyd5kv` and `xTacK4N` also failed the `bom` check; only `b6FPAf7` (0.90) happened to add `utf-8-sig`, but it also never handled epoch timestamps.
- **Ablation Hypothesis & Result:** Hypothesis: the agent fails because it only tests on tidy data it makes up itself, so if it can see one realistic production export it will notice the quirks. The single change was putting `/app/sample_transactions.csv` (UTF-8 BOM, an epoch-seconds row, a quoted `"$1,050.005"` amount, mixed-case ids, a late `PENDING` retry) into the image plus one instruction sentence telling the agent to run its fix on it. Result: all 3 trials scored 1.00. In trial `He3eqPz` the agent used `/app/sample_transactions.csv` right away (steps 23-26: it loaded the sample with the old code, rewrote `reconcile.py` with epoch and BOM handling, and ran it on the sample), and its commands now contain `sample` 11 times, `epoch` 10 times and `fromtimestamp`/`utf-8-sig` (versus 0 in Run 1). Side effect: with all trials at 1.00 both binary and dense advantage are 0, so the ablation removed the learning signal (the zero-signal trap in the other direction).

## 5. Dense Reward & Anti-Cheat Design
- **My Dense Reward Weights (`tests/test.sh`):** `reward = 0.15·CLI + 0.25·status + 0.10·(time + epoch + rank + bom + money + idcase)`. Bug 1 and Bug 2 are worth 0.40 together; Bug 3 is worth 0.60 but is split into six independent 0.10 sub-checks, each tested on its own isolated random datasets (e.g. the BOM dataset has only plain rows, the rank dataset only `Z` timestamps), so fixing one rule can never pass or fail another's check. The split gives a gradient (a trial that fixes 5 of 6 Bug 3 rules scores 0.90, not 0.40), so partial progress on the hard bug is rewarded instead of all-or-nothing, and the hard bug is worth more than the easy ones combined.
- **How `solution/hack.sh` Cheated & How I Blocked It:** `hack.sh` replaces `reconcile.py` with a stub that implements the arg check honestly but ignores the CSV and prints hardcoded JSON — enough for a naive verifier that checks one fixed CSV against one fixed answer. The hardened `test.sh` (a) generates fresh random datasets at verify time (random IDs, amounts, statuses, offsets, so there is nothing to hardcode), (b) computes expected values from the generator's own data, never from `/app`, (c) requires two independent random datasets per check to both match (every dataset is built so that the specific wrong behaviour it targets changes the answer), and (d) has an invariant: if two datasets with different correct answers produce the same non-trivial stdout, the script is ignoring its input and the total reward is forced to `0.00` (all-zero output is not flagged, so an honest-but-broken script keeps its partial credit). It fails closed (`reward.txt` starts at 0.00). Every dataset is also checked to be discriminating (the specific wrong behaviour it targets must give a different answer from the correct one).
- **Remaining Reward-Hacking Risk:** The verifier runs in the same container, as the same user and with the same Python interpreter as the agent, so a smarter agent can tamper with the environment outside /app: drop a sitecustomize.py or patch the stdlib so the verifier's own python reports success, or make reconcile.py spawn a background process that overwrites /logs/verifier/reward.txt after the verifier finishes. Fix: run the verifier with a pinned interpreter (python -I -S) from outside the agent's writable area, execute the agent's script in a sandbox as an unprivileged user with /logs and /tests unreadable and unwritable, and write the reward from a separate final process after killing all children.

## 6. AI Tool Workflow
- **AI Tool & Model Used:** I used Claude (claude.ai chat, Anthropic) to design the task and to write the task files, the verifier, the helper scripts and the first draft of this README. I used Gemini CLI (model gemini-flash-latest) as my AI coding agent for the packaging work (copying the results into jobs_summary/, running the pre-push safety checks and committing/pushing) and its exported session is in ai_transcripts/. The agent under test is `terminus-2` with `gemini/gemini-flash-lite-latest` for both runs. I ran Harbor myself, checked `nop` / `oracle` / the partial-credit run / `hack.sh` in real Harbor, and read the trajectories for section 4. The Gemini CLI session is in `ai_transcripts/`. The Claude chat is long and contained my API keys, so I did not commit it; I can share a redacted copy on request.
- **How I Avoided Prompt Leakage:** The buggy code, solution, verifier and `instruction.md` were all produced in the same Claude chat, so I could not use a separate session. To limit leakage `instruction.md` only states the CLI contract, the CSV columns, the output schema and the business rules; it never names a function, line or file section that contains a bug, and the data-format quirks (epoch timestamps, BOM, `"$1,234.50"` amounts) are only hinted at ("not always formatted uniformly"). I checked the instruction against the buggy code to confirm it contains no fix hints. The baseline result supports this: the agent did not find the quirks until the ablation gave it real data.
